Module eighteen is production operations — reliability, security, and observability. Cold open: Identity Security Cloud integrations are production software. Desk scripts that “worked on my laptop” become outages when ITDR or joiner-mover-leaver depends on them.

Outcomes: implement token reuse, four twenty-nine backoff, and pagination budgets; log request and correlation I Ds without secrets or unnecessary personal data; define service level objectives for disable and access-request automations.

Secrets: Personal Access Token per integration; rotate; revoke on offboarding; keyring locally and vault in production. Named PATs in the runbook beat a shared mystery credential. Never log bearer tokens or full identity payloads.

Rate limits live on the order of about one hundred requests per access token per ten seconds. Reuse one token per run. On four twenty-nine, reduce concurrency and use exponential backoff with jitter. Do not stampede by minting new tokens — that often makes four twenty-nines worse.

Object I D discipline: resolve by name every run. Lifecycle states, roles, and profiles differ across sandbox and prod. Hardcoded GUIDs are portable only in your dreams.

Change management: pin slash accounts slash v one style paths; keep experimental features out of prod until promoted; watch deprecation headers. Observability: request I Ds, named PATs, dashboards on error rates and provisioning lag, alarms on four oh one spikes after PAT expiry.

After mutations: GET before and after. Project standard is verify, not fire-and-forget. Async provisioning means your accept S L O and your verify S L O are different clocks — for example A P I accept under thirty seconds, lifecycle visible under two minutes for ITDR disable.

Say this in a readiness review: we reuse tokens, back off on four twenty-nine, resolve by name, verify with GET, redact personal data in logs, and name an on-call owner. Dry-run in a lower environment is required before prod mutate for bulk jobs.

Example S L O sketches: ITDR disable accept fast, verify lifecycle soon after; access request submit success tracked separately from approval lag; nightly compliance finishes dry-run report before the change window.

Failure modes: logging secrets; no alarms on auth expiry; fire-and-forget mutations; unbounded pagination that burns the rate budget; treating four oh three as “rotate the secret” without checking scopes and user level.

When you’re back at the screen: write a three-line retry policy for four twenty-nine, list three craft requirements after a lifecycle mutation, and name who gets paged when the disable verify S L O breaks.
