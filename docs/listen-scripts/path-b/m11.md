Module eleven is the SailPoint command line interface — C L I. Cold open: the C L I is how teams bootstrap the same project shape — it is not how production authenticates at three in the morning.

Outcomes: init TypeScript or other S D K projects and config via C L I; explain the C L I’s role beside spcx — the SaaS Connectivity local debugger — in connector local debug; keep C L I config free of committed secrets.

Core habit: sail sdk init typescript with a project name, then sail sdk init config. Commit the template layout, not every engineer’s personal folder taxonomy. Document the required C L I version in the README so onboarding does not drift.

Separate scaffolds: an A P I project that depends on sailpoint-api-client is not a connector project that depends on connector-sdk. Mixing those packages casually creates confused ownership and wrong deployment paths.

Connector workflows use the C L I plus spcx for local debug loops — you will deepen that in module fifteen. For now: C L I scaffolds and wires local config; spcx exercises connector commands against a running target.

Config hygiene: treat C L I config like a dot env file — local only, gitignored. Prefer keyring or environment injection over long-lived plaintext profiles. Continuous integration must inject vault secrets non-interactively. Developer workstation login patterns do not belong in headless runners.

Say this to a new hire: we scaffold with sail sdk init so every service looks alike. We never commit sail config with client secrets. Production auth is vault-managed, rotated, audited Personal Access Tokens — not your laptop C L I profile.

Team standards: pin C L I version; distinguish A P I versus connector templates; ban interactive auth in pipelines; review pull requests for accidental config commits the same way you review for secrets.

When the C L I is the wrong tool: high-volume production integrations should run as services with S D Ks and observability, not as someone re-running C L I commands. The C L I bootstraps; the service operates.

Failure modes: committing secrets in sail config; every engineer hand-rolling different TypeScript layouts; using interactive C L I login in headless prod runners; treating C L I as a substitute for secret management.

When you’re back at the screen: run or narrate sail sdk init typescript and sail sdk init config, confirm gitignore covers local config, and answer why the C L I is not enough for production auth.
